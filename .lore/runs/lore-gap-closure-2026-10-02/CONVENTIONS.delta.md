- [CONV-2026-10-02-c14d] A KNOWN HISTORICAL CONTINUITY GAP IS RECORDED EXPLICITLY AND NEVER BACK-FILLED. When records are lost with no surviving source, record the GAP as its own metadata entry (count, sources searched, date/context, honest bound) rather than reconstructing plausible content, minting placeholder IDs, or chasing a count. A gap record must state plainly that it is about the missing history and is NOT a stand-in for the lost records, and must preserve the known count discrepancy instead of quietly reconciling it. Reason: on 2026-10-02 two historical `EV-...` records became unrecoverable; a fabricated record would be an unbacked durable fact that later reads as verified evidence, and a "helpful" back-fill would permanently destroy the fact that the history is missing. See `EV-20261002-HISTORICAL-GAP-EVIDENCE-2-UNRECOVERABLE`. #added:2026-10-02
- [CONV-2026-10-02-1b3f] A RECORD COUNT IS NOT PROOF OF RECOVERY, AND AN UNRESOLVED REFERENCE IS NOT A LOST RECORD. Distinguish the two continuity statuses and never conflate them: (a) MECHANISM status — whether concurrent agents can safely write via shards and consolidation; (b) HISTORICAL COMPLETENESS status — whether prior history is fully recoverable. Alreadily-lost history must NOT by itself force serial execution, because the mechanism governs FUTURE writes. When a digest cites an entry ID that does not exist, first test whether the owning ledger is provably complete against its own measured count (a lost entry shows as a count shortfall); only if a shortfall exists is it a lost record, otherwise it is an `UNRESOLVED_HISTORICAL_REFERENCE` to be left alone, because repairing it would require guessing the author's intent. Reason: conflating the two makes agents either abandon safe concurrency over unrecoverable past records, or "repair" a digest by inventing an anchor. #added:2026-10-02
