- [DEC-2026-10-04-ESA-APPENDONLY] SCOPE DECISIONS ARE APPEND-ONLY WITH ONE NEW VERSION PER DECISION, MIRRORING 0020 EXACTLY. No governed field may ever be updated in place; the ONLY permitted mutation is stamping `superseded_at`, and a decision INSERTS a new version carrying `previous_version_id` while retiring its predecessor. - [DEC-2026-10-04-ESA-ORDERING] THE SUPERSESSION MUST RETIRE THE PREVIOUS ROW BEFORE INSERTING THE REPLACEMENT. The NULL-safe partial unique index admits only ONE current row per scope identity, so inserting first transiently holds two current rows for one identity and the index refuses it -- hit as a real failure during implementation. `decideScopeDecision` therefore UPDATEs `superseded_at` first (checking `meta.changes` and refusing with `CONCURRENT_SCOPE_SUPERSESSION` if another writer won), then INSERTs (checking `meta.changes` and refusing with `SCOPE_DECISION_NOT_INSERTED`), then writes the audit event. This is the same retire-then-insert shape already proven by `drawing-quantity-claim-writer.mjs`. Retiring first also means a refused insert leaves the location with NO current scope (UNKNOWN_SCOPE, which fails closed) rather than a stale proposal masquerading as authority. #added:2026-10-04

- [DEC-2026-10-04-ESA-TWOCOMPLETE] QUANTITY COVERAGE AND SCOPE-DEFINITION COMPLETENESS ARE NOW SEPARATE, EXPLICIT ASSERTIONS. The resolver exposes `quantityCoverageState` (COMPLETE / INCOMPLETE / UNKNOWN_SCOPE) alongside `scopeDefinitionState` (COMPLETE / PENDING / UNKNOWN), plus `approvedExpectedLocations` and `pendingScopeDecisions`, and `downstreamReady` now requires BOTH. - [DEC-2026-10-04-ESA-STALEREV] A SCOPE ROW BOUND TO A SUPERSEDED DRAWING REVISION STILL COUNTS AS SCOPE, AND THAT IS DELIBERATE. An expected-scope row states an OBLIGATION about a location, which does not become false because a PDF was re-uploaded; failing closed on every re-upload would make the authority useless. Unlike 0020 claims -- which are evidence about a specific revision and therefore DO go stale -- a scope obligation persists. The loader therefore reports `approvedOnSupersededDocumentVersion` so an engineer can see which decisions predate the current revision and may want to re-review. Recorded as a judgement call, not a derived fact. #added:2026-10-04
