- [ARCH-20261004-undfallback] A LATER FAILED interpretation does not hide an EARLIER successful one, and this is why `AI_PROVIDER_ERROR` is frequently NOT the blocker. The matching gate `currentUnderstanding` (`worker/product-matching-api.mjs:114`) selects `status IN ('COMPLETED','NEEDS_REVIEW') ORDER BY version_number DESC LIMIT 1`, so a later FAILED attempt is filtered out and the newest USABLE interpretation is returned; `resolveEffectiveUnderstandingInterpretation` applies the same eligible-status rule, and migrations 0062/0063 exist specifically so a transient failure recorded after a real one cannot permanently block the earlier valid attempt. Consequence for triage: always ask the gate, not the newest row. Two AlMousa rows (seq 22 `CWZ category fire resistant cable`, seq 71 `Combined smoke and heat detector`) carry a newest `FAILED AI_PROVIDER_ERROR` yet are `UNDERSTANDING_READY=YES` via v2/v1 respectively — their real blocker is profile readiness (`Needs Technical Review`, `approved_for_matching=0`), a governance decision, not a system fault. `handlePerItemRetry` correctly refuses them with `PER_ITEM_RETRY_EVIDENCE_CHANGED` because the evidence moved since the failed attempt. #added:2026-10-04
