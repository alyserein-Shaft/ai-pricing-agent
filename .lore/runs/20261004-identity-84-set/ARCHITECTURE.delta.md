# ARCHITECTURE delta — Product Identity authority

- [ARCH-20261004-psauth] Product Identity state is a DERIVED READ MODEL from `resolveCurrentPrimarySelection` (`worker/primary-selection-authority.mjs`), not persisted columns, and its working set is the project's downstream-eligible BOQ population (`boq_items.approved_for_downstream=1`), NOT the match-run population. Full chain: BOQ ITEM (`approved_for_downstream=1`) -> CANDIDATE SET (`product_match_candidates` joined to `product_match_runs`, non-superseded, non-rejected) -> REVIEW/GOVERNANCE STATE (`safety_decisions` + `safety_approval_requests` where `approval_type='Technical'`) -> IDENTITY RESOLVER -> DOMAIN OUTCOME (`PRIMARY_SELECTION_STATES` APPROVED/PROVISIONAL/AMBIGUOUS/UNAVAILABLE, plus codes `TECHNICAL_APPROVAL_REQUIRED`, `CURRENT_SAFETY_DECISION_REQUIRED`, `NO_CURRENT_CANDIDATE`, `CURRENT_MATCH_RUN_AMBIGUOUS`, `MULTIPLE_TECHNICAL_APPROVALS`). Three proven consequences. (1) Searching the schema for APPROVED/PROVISIONAL/UNAVAILABLE columns is a dead end BY DESIGN: states are computed per line and `boq_items` holds no identity state. (2) The identity population is `approved_for_downstream=1`, which is why a match-run-derived population UNDERCOUNTS it: an item that never ran still legitimately reports `UNAVAILABLE` and must be counted. (3) `app/domain/knowledge-product-identity-resolver.mjs` (outcomes `EXACT_UNIQUE_TARGET`/`NO_TARGET`/`AMBIGUOUS_TARGET`) is a SEPARATE Knowledge-layer fact->product resolver; it must NEVER be mapped onto `PRIMARY_SELECTION_STATES` and its outcomes are not Product Identity authority. GOV-AUTH-1 additionally guarantees a Rejected candidate cannot resolve as a primary selection even when an Approved Technical row still names it. Verified by reproducing 1/53/30 + 33/20/30 + 17 from live D1 through this path. See `worker/primary-selection-authority.mjs`, `app/domain/governed-product-identity-closure.mjs`. #added:2026-10-04

- [ARCH-20261004-viteremote] `vite.config.ts` declares `ai: { binding: "AI", remote: true }`, forcing the Cloudflare Vite plugin into remote-proxy mode, so the local dev server cannot start without an interactive `wrangler login`; `npm run dev` aborts with `You must be logged in to use wrangler dev in remote mode` and there is no plain-worker entry to run `--local` against. Consequence for governed execution: a worker route that is the SOLE writer of a governed table (here `product_match_runs`) cannot be exercised over HTTP on this machine, but can be exercised faithfully by calling the exported `handleProductMatchingApi(request, env, ctx)` in-process with a real `Request`, the real D1 binding and real single-user access mode, so `resolveApplicationContext` -> `applicationActor` auth still executes and no governance layer is bypassed; only the transport is in-process. This is the repo's own convention for these routes. A test harness driving a D1 route MUST implement `db.batch`, because `worker/product-matching-api.mjs` persists an entire match run through `env.DB.batch([...])` rather than per-statement `run()`; a shim without `batch` fails every run with the misleading `PRODUCT_MATCHING_FAILED` / `db.batch is not a function` while executing ZERO writes. See `vite.config.ts`, `worker/product-matching-api.mjs`. #added:2026-10-04
