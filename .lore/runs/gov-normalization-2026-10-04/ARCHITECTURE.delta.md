# Lore delta — normalized BOQ downstream subject bridge

- [ARCH-20261004-normalized-subject-bridge] **THE APPLIED NORMALIZED SCOPE NOW HAS ONE CANONICAL SUBJECT ID, AND IT IS A REAL `boq_items` ROW.** The audit that forced this: every downstream writer keys on `boq_item_id` with a DECLARED FK to `boq_items(id)` — `estimator_item_interpretations`, `estimator_understanding_review_versions`, `requirement_profile_versions`, `boq_requirement_links`, `product_match_runs`, `safety_decisions`. `boq_normalization_scope` originally had only `candidate_id`, so a normalized line could not be an Understanding subject at all. Rather than add a parallel subject column to six tables (a broad rewrite), `applyNormalizationReview` now MATERIALISES each accepted candidate as a real `boq_items` row under a normalization-generation extraction version, and records `subject_boq_item_id` on the scope row. `boq_items.id` is therefore the ONE stable identity that survives Understanding -> requirement applicability -> Product Identity -> matching, and every existing writer is unchanged. The subject id is DERIVED (`boqitem_norm_<reviewId>_<candidateId>`), not random, so re-Apply is idempotent and no stage invents a second identity for the same line. #added:2026-10-04
- [ARCH-20261004-governed-scope-selector] **THE DOWNSTREAM POPULATION IS CHOSEN IN EXACTLY ONE PLACE, AND RAW AND NORMALIZED ARE NEVER MIXED.** `currentBoqEvidenceFrom` semantically means RAW / CURRENT EXTRACTION EVIDENCE and is load-bearing for the raw review, so it was deliberately left untouched. A new additive selector pair was added to `worker/current-evidence-scope.mjs`: `currentGovernedBoqScopeFrom` (returns only governed subjects) and `currentDownstreamBoqScopeFrom(db, projectId)` implementing the generic invariant — IF an APPLIED current normalization generation exists, return ONLY its subjects; ELSE return the explicitly permitted pre-normalization raw scope. `activeRows` in `worker/estimator-understanding-api.mjs` now resolves through it, so before Apply the 21 are not falsely exposed and after Apply the population is exactly 21, never 90+21. #added:2026-10-04
