# DECISIONS.delta.md

- [DEC-20261004-AUTO-AUTHORITY-IS-DETERMINISTIC-ONLY] `BOQ_NORMALIZATION_AUTO_AUTHORITY_V1` may auto-approve a normalized candidate only when ALL deterministic checks pass against persisted evidence. AI confidence can NEVER grant authority: the evaluator takes no confidence input at all, and the decision record exposes no confidence/score/probability field, so there is nothing to launder into authority.
- [DEC-20261004-AUTO-DECISIONS-ARE-SYSTEM-POLICY] Auto-approved decisions are persisted as explicitly NON-HUMAN: `decision_actor_type = SYSTEM_POLICY`, `decision_mode = AUTO_APPROVED`, `policy_id = BOQ_NORMALIZATION_AUTO_AUTHORITY_V1`, `humanActor = null`. Recording them as `omair` / `Omair` would fabricate human approval, and `local-development-user` is never quoted as a decision-maker.
- [DEC-20261004-APPLY-REASON-NAMES-THE-REAL-ACTOR] The Apply audit reason no longer hardcodes the word "human"; it branches on `human.role === "SYSTEM_POLICY"` so a policy-driven apply is never recorded as a human apply and the authority trail stays truthful.
- [DEC-20261004-AUTO-APPLY-IS-A-GATE-NOT-A-WEAKER-PATH] `auto-apply` evaluates the policy and, only on eligibility, calls the UNCHANGED `applyNormalizationReview`. No parallel implementation, no relaxed validation, no separate materialization path. All canonical re-derivation, currency re-check, anchor preservation and supersession rules still apply.
- [DEC-20261004-SEMANTIC-AMBIGUITY-IS-DEFERRED-NOT-RESOLVED] A terminology difference between contributing rows (e.g. `Combined smoke and heat sensor` vs `... detector`) does not block normalization when quantity, unit and anchors are deterministic. It is recorded as `SEMANTIC_AMBIGUITY_DEFERRED_TO_UNDERSTANDING` and belongs to BOQ Understanding. The normalization layer never silently resolves terminology and never asserts a downstream technical classification.
- [DEC-20261004-GOVERNANCE-CHECKS-ACCUMULATE-NEVER-SHORT-CIRCUIT] The evaluator deliberately has NO early `continue`. An earlier failure must never be able to mask a later governance check, otherwise the ORDER of checks would decide whether a deleted or dangling source row is caught. Regression test `7b` guards this.
- [DEC-20261004-EVERY-RAW-ROW-CLAIMED-EXACTLY-ONCE] Cross-candidate anchor ownership is a first-class material-scope check: zero claims means normalization dropped source evidence, two or more means it double-counted. Both are always human-owned. This is what makes `allSourceRowsPreserved` and `everySourceRowClaimedExactlyOnce` genuinely distinct claims rather than restatements.
- [DEC-20261004-UNIT-COMPARISON-CANONICALIZES-BOTH-SIDES] A candidate may legitimately declare a raw surface form (`no`, `ls`) while its source rows carry the normalized form (`Each`, `Lump Sum`). Comparing a canonical form against a raw string reports a conflict where the two sides agree exactly. Both sides are canonicalized; a REAL conflict is when canonical forms differ or when either side falls outside the closed vocabulary. An unknown unit is never guessed.
- [DEC-20261004-SUBJECTS-INHERIT-AND-NEVER-OVERSTATE] A normalized subject derives `section_path` from its own contributing rows and takes the MINIMUM `extraction_confidence` across them. A normalized line must never appear more certain than the evidence it was derived from.
- [DEC-20261004-NORMALIZATION-OUTPUT-IS-NOT-A-NORMALIZATION-SOURCE] Extractions with `extraction_method = 'Controlled Normalization'` are the OUTPUT of a review, never a source a review can be built from. They are excluded from current-source resolution and from the Apply currency check; otherwise creating the subject extraction would immediately make its own source stale and the review impossible to re-evaluate or re-apply.
- [DEC-20261004-SQL-NULL-COMPARISON-NEEDS-AN-IS-NULL-GUARD] Every `Controlled Normalization` exclusion uses explicit `(x IS NULL OR x <> 'Controlled Normalization')`. In SQL `NULL <> 'x'` evaluates to NULL, not TRUE, so a bare `<>` silently drops every extraction row with no recorded method and breaks currentness.
- [DEC-20261004-REAPPLY-IS-A-NO-OP-NOT-A-409] `auto-apply` short-circuits to the canonical Apply's idempotency result when the review is already `APPLIED`. Otherwise the policy gate would report `NORMALIZATION_REVIEW_NOT_OPEN` and turn a harmless repeat into an error.
- [DEC-20261004-SUPERSEDED-REVIEW-STAYS-APPLIED] Supersession is recorded on the governed SCOPE, which is what downstream readers resolve. An older review keeps `status = 'APPLIED'` as the historical record of what it applied; rewriting it to `SUPERSEDED` would falsify history. Its scope rows are superseded, so it contributes nothing to the live scope.
- [DEC-20261004-REVIEW-RESUME-TESTS-ASSERT-CANONICAL-AUTHORITY] The client-hash-cache gate (`documentHashes[logical_name]` resolved via `controlledBoqShaFor`) made the button invisible in the live UI because that cache is hydrated only from localStorage, which `browserBusinessPersistenceEnabled = false` disables. The suite now asserts canonical `document.sha256` authority AND explicitly asserts the old gate is ABSENT, so the outage cannot silently return.
- [DEC-20261004-UI-REPORTS-THE-SERVER-VERDICT] The `normalized-boq-policy-banner` renders whatever `evaluate-auto-approval` returns, or the live scope count when the review is already applied. The client never computes eligibility, and a failed policy read shows no banner rather than fabricating one. Human review UI is retained for inspection and audit.
