# CONVENTIONS shard -- run idp-control-6-addresses-2026-10-02. Explicit-count discipline and additive resolver contracts.

- [CONV-2026-10-02-2f18] AN EXPLICIT COUNT MUST NEVER OVERRIDE A ZERO-ADDRESS DEVICE, AND A MALFORMED COUNT MUST FAIL CLOSED. Two failure modes are guarded separately. First, ordering: the `NOT_SLC` and `consumesSlcAddress === false` branches return zero BEFORE the explicit count is consulted, and the ignored value is reported back as `ignoredExplicitCount` with a reason rather than being silently dropped. This is the structural guarantee that the accepted NAC architecture cannot convert appliance quantity into addresses, because a stated count of 4380 on a NAC appliance still yields 0. Second, validation: `addressesConsumed` is validated even on the paths where it will not be used, so a malformed value is never quietly ignored. Prefer refusing a count to defaulting it, because a silent fallback to 1 would under-count a proven 6- or 10-address module by 6x or 10x with no error raised. #added:2026-10-02
- [CONV-2026-10-02-8c05] A RESOLVER CONTRACT SHOULD WIDEN ADDITIVELY, NEVER BREAK ITS CALLERS. `slcAddressDemandForAllocations` previously took a resolver returning a bare address-model STRING. It now accepts EITHER that string (unchanged legacy contract) OR an object carrying `{ addressModel, addressesConsumed }`, so every existing caller keeps working untouched and the new capability is opt-in at the call site. The only production consumer, `panelDemandFromAllocations`, forwards the resolver straight through, so it inherits multi-point support with no wiring change. #added:2026-10-02
