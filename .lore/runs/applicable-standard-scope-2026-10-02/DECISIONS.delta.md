- [DEC-2026-10-02-6b3f] `APPLICABLE_STANDARD_SCOPE_MODEL_BLOCKER` -- UL STANDARDS ARE PRODUCT-FAMILY-SPECIFIC AND THE CURRENT SCOPE KEY CANNOT BIND THEM. A universal project-wide `UL 864` fact is WRONG and is withdrawn: UL 864 covers fire-alarm control units and their accessories only, and our own canonical library proves the per-family split (UL 864 = IFP-2100HV / RA-2000 / SLM-318; UL 268 = IDP-PHOTO-IV, B200S-IV; UL 268A = DNR, DNRW duct detectors; UL 521 = IDP-PTIR-IV heat detectors; UL 38 = IDP-PULL-SA manual stations; UL 464 audible and UL 1971 visual notification appliances). The blocker is NOT the absence of a scope concept -- `resolveScopedFacts` in `app/domain/engineering-knowledge.mjs` supports `Product Family` scope with precedence BOQ Item > Product Family > Project > Global, and the first fact per predicate wins. The blocker is that the scope key does not carry governed family names. `resolveScopedFacts` matches `fact.scopeId === context.productFamily` by EXACT string equality, and `productFamily` is computed as `approvedProductFamily || subcategory || category`. This project has ZERO `Understanding` engineering facts, so `approvedProductFamily` is always undefined, and `subcategory` is NULL on all affected items -- therefore productFamily resolves to the raw CATEGORY labels `"Control Panel"`, `"Module"` and `"Detector"`, while the existing Product-Family-scoped `applicable_standard` facts use governed names `"Fire Alarm Control Panel"`, `"Control Module"` and `"Duct Detector"`. Exact equality fails on every one, so no scoped standard can bind. #added:2026-10-02
- [DEC-2026-10-02-1e7c] SCOPING A PRODUCT STANDARD TO THE CATEGORY LABEL `"Detector"` IS DEMONSTRABLY UNSAFE AND WAS REFUSED. Eleven BOQ items on this project resolve to `productFamily = "Detector"`: 3 duct detectors, 5 heat detectors and combined smoke+heat lines. A single `"Detector"`-scoped `applicable_standard` would therefore hand **UL 268A to heat detectors whose correct standard is UL 521** -- silently, with readiness passing, because the engine's only test is `standards.length ? true : null`. That is precisely the cross-family inheritance the human prohibited, merely inverted, and it would have looked like a clean pass. The same objection applies to `"Control Panel"` and `"Module"`: they are category labels rather than governed family names, so scoping a product standard to them bypasses the governed vocabulary and will silently misapply as classification improves. The correct dependency is that `productFamily` be assigned a governed family name first, which is a classification decision and is explicitly out of scope for this task. #added:2026-10-02
