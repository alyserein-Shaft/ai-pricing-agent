# ARCHITECTURE delta — BOQ Understanding is a governed pilot, not a free function

- [ARCH-20261004-undpilot] BOQ Understanding has exactly TWO canonical write routes, both governed, and neither will process an arbitrary item on demand. Sole writer of `estimator_item_interpretations` is `executeRun` (`worker/estimator-understanding-api.mjs:587`). (1) CONTROLLED PILOT: `POST /api/projects/{projectId}/estimator-understanding/run`, body must be exactly `{mode:"CONTROLLED_PILOT", itemIds:[...], manifestFingerprint}` and `authorizeControlledPilotSelection` rejects with `PILOT_ITEM_NOT_AUTHORIZED` for any item absent from the CURRENT manifest's `itemIds`. The manifest is `buildBoqUnderstandingPilotManifest` (`app/domain/boq-understanding-pilot.mjs:303`), which classifies each row into GOVERNED_PRIMARY / CROSS_SYSTEM_EXPLORATORY / DATA_QUALITY_EXCLUDED via `exclusionReasonsFor` (line 121), then selects by `selectPrimaryByDistinctFamily` — ONE ROW PER TAXONOMY FAMILY under caps — after removing rows that already carry any interpretation (Sprint 1.9 fairness rotation). (2) PER-ITEM RETRY: `POST /api/boq-items/{itemId}/estimator-understanding/retry`, eligible ONLY when the latest attempt is `status='FAILED'` with a code in `TRANSIENT_MODEL_FAILURE_CODES` (`AI_OUTPUT_INVALID_SCHEMA`, `AI_OUTPUT_INVALID_UNSUPPORTED_FIELD`, `AI_OUTPUT_INVALID_CONFIDENCE`, `AI_PROVIDER_ERROR`), the current `interpretationInputFingerprint` still equals the failed attempt's, and fewer than `MAX_PER_ITEM_RETRY_ATTEMPTS` (3) failures exist at that fingerprint+`prompt_version`. So "missing understanding" is NOT a defect that deterministic processing can always clear: a row can be fully eligible and still be unprocessable because a governed selection currently holds its family slot. Also note the matching gate `currentUnderstanding` accepts ONLY `status IN ('COMPLETED','NEEDS_REVIEW')` (`worker/product-matching-api.mjs:114`), so an `AI_UNAVAILABLE` row would NOT unblock matching — provider readiness must be verified BEFORE running understanding, never after. See `worker/estimator-understanding-api.mjs`, `app/domain/boq-understanding-pilot.mjs`, `app/domain/boq-understanding-engine.mjs`. #added:2026-10-04

- [ARCH-20261004-hdgexcl] The governed BOQ Understanding data-quality gate excludes a row as `Heading-like row` when its description matches `genericHeading` (`/^(?:for\s+.+|general|scope(?:\s+of\s+works?)?|preliminaries|notes?|description|bill\s+of\s+quantities|.+\s+system)$/i`) AND `genericProductEvidence(row)` is empty. Because the alternation ends in `.+\s+system$`, ANY product row whose description legitimately ends in the word "system" is excluded — e.g. Al Mousa rows "Control of HVAC equipment, smoke exhaust fans, duct heaters and interfacing with BMS system". This is a REAL governed refusal, not a transient failure: such a row can never receive a current interpretation, so its downstream Product Identity line is permanently `BOQ_UNDERSTANDING_REQUIRED`. It is a classification judgement (is this a heading or a deliverable row?), not an automation limit, so it must be resolved by a GOVERNED classification/evidence decision and must never be side-stepped by relaxing the regex or hand-inserting an interpretation. #added:2026-10-04

- [ARCH-20261004-provcert] BOQ Understanding provider credentials are read from the `env` OBJECT passed to the handler (via `nvidiaReadiness`/`nvidiaApiKey`), NOT from `process.env`, so an in-process driver must forward `NVIDIA_API_KEY`/`NVIDIA_BASE_URL` into that object exactly as Wrangler vars would. Without them `boqUnderstandingProviderReadiness` reports `Misconfigured — NVIDIA_API_KEY is required for the hosted NVIDIA NIM endpoint` and `createConfiguredBoqUnderstandingProvider` returns null, which silently yields `AI_UNAVAILABLE` interpretation rows that do NOT satisfy the matching gate. Verify readiness BEFORE running any understanding batch. Readiness is configuration-only and carries no health claim. See `worker/boq-understanding-provider.mjs:233,620`. #added:2026-10-04
