- [CONV-2026-10-02-1b6c] SEPARATE THE PRODUCT-LISTING BASIS FROM THE DESIGN-CODE BASIS IN EVERY FIRE ALARM FACT, AND LABEL WHICH ONE A FIELD MEANS. The recurring failure is a single `standard` field absorbing both UL/FM listing and the local installation code, so a catalogue search silently inherits a design regime it was never asked about. Read the field's `whyNeeded` before assigning a value: "product search boundary" and "compliance or compatibility" mean a listing basis, while coverage, layout, spacing and notification design mean the governing code. Never satisfy a listing question with a code, and never let a listing value stand in for a code. #added:2026-10-02
- [CONV-2026-10-02-7d55] NEVER WRITE A GOVERNED VALUE DIRECTLY INTO A DERIVED PROFILE. `requirement_profile_versions.profile` is regenerated by `executeRequirementProfile` on every `recalculate`, superseding the previous version, so any hand-edited standard/attribute inside that JSON is destroyed at the next regeneration. Governed values belong in canonical facts or `applicable_standard` Source Facts that the engine reads at generation time; the profile is output, never input. #added:2026-10-02
